4. Bencoding and the anatomy of a .torrent file

4.1 What bencoding is

Bencoding is the compact data format used by BitTorrent metainfo files and some protocol extensions. It supports four value types: byte strings, integers, lists, and dictionaries. It is not JSON, although decoded data can look similar in a console.

TypeBencoded formDecoded meaning
Byte string4:spamFour bytes containing spam.
Integeri42eThe integer 42. i starts it and e ends it.
Listl4:spam4:eggseA list containing spam and eggs.
Dictionaryd3:cow3:moo4:spam4:eggseKeys and values: cow -> moo, spam -> eggs.

4.2 Byte strings are length-prefixed

In 4:spam, the 4 describes the number of bytes after the colon, not necessarily the number of visible characters. UTF-8 characters can use more than one byte, so protocol code must think in bytes.

Characters and bytes are not always the same count

JavaScript
Buffer.byteLength('hello', 'utf8'); // 5
Buffer.byteLength('£', 'utf8');     // 2

4.3 Integers

An integer begins with i and ends with e. The digits between them are base-ten ASCII. Examples are i0e, i123e, and i-7e. Canonical bencoding does not use leading zeros, so i03e is invalid.

4.4 Lists

A list begins with l and ends with e. Its elements are placed one after another. Because every value has a complete representation, a decoder knows exactly where one element finishes and the next begins.

A list containing the byte string spam and integer 42

Text
l4:spami42ee
^       ^
list    end

4.5 Dictionaries

A dictionary begins with d and ends with e. Keys are bencoded byte strings followed immediately by their values. Canonical dictionaries sort keys by their raw byte-string values. This ordering matters when calculating a v1 info hash.

Dictionary with name and length

Text
d4:name9:puppy.jpg6:lengthi124234ee

4.6 Decode and encode with bencode 4.0.1

bencode package basics

JavaScript
import bencode from 'bencode';

const encoded = Buffer.from('d3:cow3:moo4:spam4:eggse');
const decoded = bencode.decode(encoded);
console.log(decoded.cow.toString('utf8')); // moo

const again = bencode.encode(decoded);
console.log(again.toString('utf8'));

The package returns byte strings as Buffer values. That is correct and important: not every byte string is human-readable text. The pieces field, for example, contains raw SHA-1 hashes and must not be decoded as UTF-8.

4.7 A torrent file at a high level

Typical decoded single-file v1 torrent

Text
{
  announce: <Buffer ...>,
  'announce-list': [ ... ],
  'creation date': 1462355939,
  'created by': <Buffer ...>,
  info: {
    name: <Buffer ...>,
    length: 124234,
    'piece length': 16384,
    pieces: <Buffer ...>
  }
}
FieldMeaning
announcePrimary tracker URL.
announce-listOptional tiers of alternative tracker URLs.
creation dateOptional Unix timestamp describing when the torrent was created.
created byOptional name/version of the program that made the torrent.
info.nameSuggested file name for a single-file torrent, or top-level folder for a multi-file torrent.
info.lengthFile size in bytes for a single-file torrent.
info.filesArray of files for a multi-file torrent. This replaces info.length.
info.piece lengthNormal number of bytes in each piece.
info.piecesAll expected v1 piece SHA-1 hashes joined together. Each hash is exactly 20 bytes.

4.8 Why pieces.length / 20 gives the piece count

SHA-1 always returns 20 bytes. If info.pieces contains 400 bytes, it contains 400 / 20 = 20 piece hashes. The piece at index 0 uses bytes 0-19, index 1 uses bytes 20-39, and so on.

4.9 The info hash

For a v1 torrent, the info hash is SHA-1 applied to the exact bencoded info dictionary. It identifies the torrent when speaking to a tracker or peer. It is not the hash of the downloaded file as one whole object.

Simple educational calculation

JavaScript
const encodedInfo = bencode.encode(torrent.info);
const hash = crypto.createHash('sha1').update(encodedInfo).digest();
i
A subtle production detail

The safest production parser hashes the exact raw byte slice occupied by the info dictionary in the original .torrent file. Decode-then-re-encode works for normal canonical torrents, which is what this guide assumes, but a non-canonical file could re-encode differently.

4.10 Single-file versus multi-file torrents

A single-file torrent has info.length. A multi-file torrent has info.files, where each item contains a length and path components. The bytes still form one continuous logical stream for piece hashing. Supporting multiple output files therefore requires mapping stream offsets across file boundaries.
