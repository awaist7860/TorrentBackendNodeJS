11. Reassemble complete messages from a TCP stream

TCP does not promise this

11.1 The common beginner mistake

TCP does not promise this

JavaScript
socket.on('data', (data) => {
  // Wrong assumption: data is exactly one complete BitTorrent message.
});

A data event can contain half a message, exactly one message, or several messages joined together. This depends on operating-system buffering, packet sizes, timing, and the network. Correct code saves incomplete bytes and repeatedly extracts complete frames.

11.2 Handshake length differs from normal messages

The first incoming application message is the handshake. Its length is pstrlen + 49, so we need at least one byte before we know its total length. Later messages store a four-byte length prefix and occupy prefix + 4 bytes in total.

11.3 Complete framing function

Persistent receive buffer

JavaScript
function onWholeMessage(socket, callback) {
  let saved = Buffer.alloc(0);
  let waitingForHandshake = true;
 
  socket.on('data', (received) => {
    saved = Buffer.concat([saved, received]);
 
    try {
      while (true) {
        if (waitingForHandshake) {
          if (saved.length < 1) return;
 
          const handshakeLength = saved.readUInt8(0) + 49;
          if (saved.length < handshakeLength) return;
 
          const handshake = saved.subarray(0, handshakeLength);
          saved = saved.subarray(handshakeLength);
          waitingForHandshake = false;
          callback(handshake, true);
          continue;
        }
 
        if (saved.length < 4) return;
 
        const messageLength = saved.readUInt32BE(0) + 4;
        if (messageLength > 2 * 1024 * 1024) {
          throw new Error('Peer sent an unreasonably large message.');
        }
        if (saved.length < messageLength) return;
 
        const message = saved.subarray(0, messageLength);
        saved = saved.subarray(messageLength);
        callback(message, false);
      }
    } catch (error) {
      socket.destroy(error);
    }
  });
}

Walkthrough

1. saved begins empty and survives between data events because it is closed over by the event callback.

2. New bytes are concatenated after any previously incomplete bytes.

3. During the first frame, one byte reveals the handshake length.

4. If the full frame is not present, return and wait for another data event.

5. When a frame is complete, take it from the front of saved and leave the remainder for the next loop iteration.

6. After the handshake, read the normal four-byte length prefix.

7. Reject unreasonable lengths before waiting for or allocating around attacker-controlled values.

8. The while loop means several complete messages in one data event are all delivered to the callback.
